# GODOT GAME — ПОЛНЫЙ АУДИТ И ПОИСК ОШИБОК

Ты работаешь как **Senior Godot Engineer / QA Engineer / Debugging Agent**.

Твоя задача — самостоятельно проверить весь проект Godot на наличие ошибок, багов, потенциальных проблем и неправильных реализаций, а затем по возможности исправить их.

## 1. ГЛАВНОЕ ПРАВИЛО

Не ограничивайся очевидными синтаксическими ошибками.

Проверяй:

* ошибки GDScript;
* runtime errors;
* ошибки загрузки сцен;
* неправильные NodePath;
* отсутствующие ресурсы;
* сломанные ссылки на сцены, скрипты, текстуры и аудио;
* ошибки сигналов;
* неправильные подключения сигналов;
* null references;
* неправильное использование `@onready`;
* проблемы с `await`;
* проблемы с `queue_free()`;
* ошибки жизненного цикла Node;
* неправильное использование `_ready()`, `_process()`, `_physics_process()`;
* ошибки физики и коллизий;
* проблемы с CharacterBody2D / CharacterBody3D;
* ошибки AnimationPlayer / AnimatedSprite / AnimationTree;
* проблемы с UI;
* проблемы с Input Map;
* проблемы с сохранением данных;
* ошибки autoload;
* проблемы с singleton;
* циклические зависимости;
* проблемы производительности;
* утечки объектов;
* лишние процессы `_process()` / `_physics_process()`;
* слишком частые операции;
* потенциальные race conditions;
* ошибки таймеров;
* проблемы с потоками;
* ошибки загрузки ресурсов;
* неправильные настройки проекта;
* проблемы совместимости с текущей версией Godot;
* предупреждения, которые потенциально могут превратиться в реальные баги.

## 2. СНАЧАЛА ИССЛЕДУЙ ПРОЕКТ

Проверь:

* `project.godot`
* все `.gd`
* все `.tscn`
* все `.tres`
* все `.res`
* все `.json`
* все используемые ассеты и ресурсы;

* связанные сцены;
* UI;
* системы сохранения;
* игровые менеджеры;

Определи:

1. главную сцену;

3. основные игровые системы;
4. зависимости между системами;
5. критические точки отказа.

Не спрашивай меня, какие файлы проверять. **Проверь весь проект самостоятельно.**

## 3. ПРОВЕРКА КОДА

Проведи статический анализ всего GDScript-кода.

Для каждого подозрительного места проверь:

* существует ли вызываемый метод;

* правильный ли у неё тип;
* существует ли Node;

* существует ли ресурс;

* не вызывается ли объект после `queue_free()`;

## 6. ЗАПУСК ПРОЕКТА

Если у тебя есть возможность запускать Godot через терминал или доступный инструмент, обязательно:

1. запусти проект;
2. дождись ошибок;
3. собери stdout/stderr;
4. проверь Godot debugger;
5. проверь parser errors;
6. проверь runtime errors;
7. проверь warnings.

Используй фактические логи, а не предположения.

Если проект не запускается — сначала исправь критическую ошибку запуска, затем продолжай аудит.

* запуск игры;

* начало игры;
* управление персонажем;

Для каждого сценария ищи состояние, при котором игра может:

* зависнуть;
* выдать ошибку;
* потерять данные;
* создать дубликаты;

## 8. ПРОВЕРКА ЛОГИКИ

Не ищи только технические ошибки.

Ищи логические баги:

* условие никогда не выполняется;
* условие всегда выполняется;
* неправильные значения;
* неправильный порядок действий;
* переменная никогда не обновляется;
* состояние не сбрасывается;
* объект создаётся несколько раз;
* объект никогда не уничтожается;
* сигнал приходит несколько раз;
* событие никогда не приходит;
* UI показывает неправильное состояние;
* счёт/здоровье/ресурсы могут уходить в некорректные значения.

## 9. ПРОВЕРКА ПРОИЗВОДИТЕЛЬНОСТИ

Найди потенциальные bottleneck'и:

* тяжёлый код в `_process()`;
* тяжёлый код в `_physics_process()`;
* частые `get_node()`;
* частые `find_child()`;
* ненужное создание объектов;
* постоянная загрузка ресурсов;
* лишние сигналы;
* слишком много instantiated Nodes;
* чрезмерное количество collision checks;
* лишний `queue_redraw()`;
* лишние обновления UI.

Отделяй реальные проблемы от теоретических.

Не оптимизируй код без необходимости.

## 10. КЛАССИФИКАЦИЯ ОШИБОК

Каждую найденную проблему классифицируй:

### CRITICAL

Игра не запускается или основной функционал сломан.

### HIGH

Серьёзный runtime bug или проблема, которая может ломать игру.

### MEDIUM

Функциональная ошибка, которая проявляется при определённых условиях.

### LOW

Небольшая ошибка, warning или потенциальная проблема.

### OPTIMIZATION

Не ошибка, но есть возможность улучшить производительность/архитектуру.

## 11. ИСПРАВЛЕНИЕ

После обнаружения ошибок:

1. сначала исправляй `CRITICAL`;
2. затем `HIGH`;
3. затем `MEDIUM`;
4. затем `LOW`;
5. затем рассматривай optimization.

Не переписывай проект целиком.

Сохраняй существующую архитектуру, если для исправления проблемы это не требуется.

Не создавай ненужную сложность.

## 12. ВАЖНО

Не делай вид, что ошибка исправлена.

После каждого существенного исправления:

1. повторно проверь изменённый код;
2. проверь связанные сцены;
3. снова запусти проект;
4. проверь, не появилась ли новая ошибка.

Используй принцип:

**FIX > VERIFY > TEST > RECHECK**

## 13. НЕ СПРАШИВАЙ МЕНЯ БЕЗ НЕОБХОДИМОСТИ

Не задавай вопросы вроде:

* "Какой файл проверить?"
* "Что мне открыть?"
* "Что делать дальше?"
* "Можно ли проверить эту сцену?"

Самостоятельно исследуй проект и принимай технические решения.

Спрашивай меня только тогда, когда требуется решение, которое невозможно определить из самого проекта.
